# 玻璃材质验证

按修改范围选择验证项，区分源码判断、纯逻辑检查和真实 macOS 窗口观察。不要把编译成功或截图中的半透明填充当成真实背景取样的证明。

## 静态与编译检查

- 搜索材质辅助函数的实际调用位置：目标面板注册了几何、透明背景生效、统一提交被执行。
- 检查 runtime guards 覆盖新类的构造与类型转换；按所选后端分派更新和清理。
- 检查目标平台依赖和 Cargo features。运行项目规定的格式化、目标编译及受影响的测试。
- 非 macOS 构建保持平台隔离；无法访问对应 target 或旧 macOS 时，说明验证范围，不把宿主机检查写成跨平台验证。
- 纯逻辑测试适合坐标转换、能力选择、面板增删、关闭恢复和多个窗口隔离。新增测试应覆盖可观察行为或实际回归。
- 原生桥接只在 macOS 的非测试构建中编译（`#[cfg(all(target_os = "macos", not(test)))]`）。测试构建里只被原生侧读取的字段会触发 dead-code 警告，在 `-D warnings` 下失败；用 `cfg_attr(..., allow(dead_code))` 精确放行。

## 无头 GPUI 测试

测试中 `supported()` 恒为 false，所以要直接写入玻璃全局，强制走玻璃布局。原生玻璃此时是惰性的，但整套 GPUI 外框都会被构建、布局和 paint，“hover style already set” 这类构造错误就能在这里暴露。实际有效的模式：

```text
set_glass(on):
    cx.set_global(Glass(on))
    重新执行应用的主题流程（它以 glass::adapt_theme 收尾）
    window.refresh()；run_until_parked()

测试：
    先在关闭状态下记录关键元素的 debug_bounds
    set_glass(true)
    断言玻璃几何：悬浮面板距窗口边 INSET，胶囊按钮 30×30 且垂直居中于头部，
                 搜索条 48 高、结果卡与其等宽且相距 8
    逐个把鼠标移到每个玻璃按钮和列表行上，run_until_parked()
    set_glass(false)，断言关键元素的 bounds 与开启前完全一致
```

- 让测试窗口的根是 GPUI Kit `Root`，否则 `sync_window` 中清除 `Root` 背景的分支不会执行。
- 每个窗口各写一个：主窗口、设置窗口（逐页点击导航，在每页悬停控件）、预览窗口。
- 统一控件尺寸后，加一个分别开启和关闭玻璃、逐页检查按钮、下拉和分段选项高度的测试。
- 确认新测试真的能失败：例如胶囊按钮尺寸的断言在玻璃样式未生效时会不通过。

## 视觉检查前先做原型

不确定合成方式时，先用一个约一百行的 Swift 程序模拟 GPUI 的视图栈：透明窗口，`NSGlassEffectContainerView` 中放几个 `NSGlassEffectView`，上面一层带孔的实色视图并绘制文字。分别试“玻璃在上”“玻璃在下并镂空”“玻璃在下不镂空”，几分钟就能看清：玻璃在上会模糊上层文字；内容区中间的胶囊若采样桌面，看起来像窗口上的洞。

## 真实窗口中的背景取样

用临时内容与隔离的配置运行应用；只有获得实际观察结果才能报告视觉检查通过。

| 目标 | 操作 | 观察 |
| --- | --- | --- |
| 桌面取样 | 将明显的明暗/彩色图案置于应用后方，再移动窗口 | 材质随后方内容变化；普通透明孔没有被误认为玻璃 |
| 正文取样 | 在玻璃控件后方滚动文字、图片或彩色内容 | 玻璃内取样随正文变化，位置正确 |
| 几何同步 | 改变窗口大小，显示/隐藏面板，检查动画中间态 | 玻璃边缘、圆角和控件位置一致，无残留或额外的迟滞动画 |
| 裁剪 | 滚动、折叠或将面板滑出边缘 | 原生材质遵循 GPUI 可见范围，无越界背景或漏孔 |
| 融合 | 让两个符合条件的玻璃面板靠近/离开 | 已设置的容器距离确实产生预期融合及分离 |
| 生命周期 | 创建两个窗口，独立更新或关闭其中一个 | 面板不会跨窗口串位；关闭后没有 retained 视图或注册项残留 |
| 禁用与恢复 | 切换应用已有的材质设置并重新开启 | 原生视图移除，原有背景恢复，再次启用可重建 |

如果产品没有动态切换入口，在实现的生命周期边界验证关闭/重开；不要为了检查而扩大设置界面的范围。

### 截图的局限与隐私

- 单窗口截图（例如 `screencapture -l <window-id>`）不包含窗口后方的内容：取样桌面的玻璃显示为平灰，控件周围还可能出现斑块。它适合检查布局、圆角和控件位置，不能证明折射效果，也不要为其中的伪影改代码。
- 按进程号找到自己启动的窗口，不要按应用名查找，因为用户可能同时开着正式版。不要截全屏或屏幕区域：窗口位于其他桌面空间时，区域截图会拍到用户自己的内容。误截后立即删除。
- 窗口位于非活动的桌面空间或屏幕锁定时，截图会失败或拿到旧帧；先确认窗口在屏、会话未锁定。
- 用隔离的配置目录运行测试实例，避免改动用户的设置和会话。共用 target 目录时，构建后把二进制复制到私有路径再运行，防止被用户的构建覆盖。
- 跳过授权、自动打开窗口这类调试入口只留在本地，交付前删除。
- 真实折射以用户在自己屏幕上的观察为准。用户自行验收视觉效果时，交付代码和无头检查即可，不必为了截图添加调试入口或启动应用。

## 外观、交互与系统设置

- 检查 light/dark 和实际支持的自定义主题；文字、图标、分隔线保持可读，玻璃 appearance 与主题一致。
- 检查 hover、pressed、selected、disabled、keyboard focus 和弹出菜单/对话框；关键状态不能只靠透出背景的颜色区分。
- 检查项目支持的 UI 缩放和不同显示 backing scale；玻璃与控件对齐，圆角和窗口控制按钮位置正确。
- 检查窗口激活/失焦；原生材质与 GPUI 控件状态协调。
- 检查 macOS“减少透明度”与“减少动态效果”：确认系统材质遵循偏好，并调整应用自己的透明填充和动画。查询系统设置时核对当前 AppKit API；不要假定系统已经处理 GPUI 动画。

## 系统降级

在 macOS 26+ 验证真正的 `NSGlassEffectView` 路径。可用旧 macOS 时验证 `NSVisualEffectView` 路径的首次创建、圆角更新及关闭；不可用时标明未实机验证，并覆盖能力选择的纯逻辑。

测试环境没有真实 `NSWindow` 时使用关闭状态或测试适配器；这些检查不能代替原生材质验证。即使单元测试绕开原生调用，也应确保平台桥接代码被目标编译检查覆盖。

## 问题定位

| 症状 | 优先检查 |
| --- | --- |
| 完全实色 | 窗口透明属性、Root/包装层/面板的覆盖背景、原生视图挂载顺序 |
| 只看到裸露桌面 | 材质视图是否实际创建、有效 frame、背景取样及系统偏好 |
| 玻璃不响应正文变化 | 正文是否位于材质后方；单个上方 GPUI 图层无法被下方材质采样 |
| 旧系统类查找 panic | `alloc()`、`class()` 或泛型 downcast 是否绕过运行时保护 |
| 相邻面板没有融合 | 容器的 contentView 后代关系、spacing、面板样式及实际距离 |
| 拖动或缩放时错位 | flipped 坐标、父视图偏移、backing scale、裁剪、隐式动画 |
| 重绘后玻璃消失 | 帧收集是否被缓存跳过，提交是否误把不完整集合当成全量集合 |
| 启动或悬停时 panic “hover style already set” | 对 GPUI Kit `Button` 或已带 hover 的辅助函数又调用了 `.hover()`/`.active()`；改为构造时传入状态色 |
| 选中、禁用的按钮与普通状态看起来一样 | 按钮实例上设置了 `.bg()`，Button 会在这些状态中重放它；改用主题 token |
| 玻璃出现在错误的窗口，或另一个窗口没有玻璃 | 该窗口是否在 render 开头 `sync_window`、根元素最后 `commit` |
| 关闭玻璃后颜色没有复原 | 是否只调用了 `adapt_theme`；要重新执行完整的主题流程 |
| 切换玻璃后红绿灯不动 | 位置只在创建时设置；状态变化时调用 `Window::set_traffic_light_position` |
| 测试中 panic：找不到主题全局 | 绘制路径用了 `cx.global::<Palette>()`；改用 `try_global` |

交付说明应简短列出实际接入区域与背景来源、系统支持/降级，以及执行过的检查和剩余的实机验证限制。
